# Chat 输入框附件 @ 引用设计

- 日期：2026-08-24
- 状态：方向已确认，待书面审阅
- 范围：`core-ai-frontend`、`core-ai-api`、`core-ai-server`

## 1. 背景

当前 Chat 输入框支持上传或粘贴图片、视频、PDF 和普通文件。发送时，附件通过
`SendMessageRequest.attachments` 进入服务端：图片和视频进入多模态内容，PDF 以 URL 提示，
普通文件上传到 Sandbox 后以 `/tmp/<fileName>` 提示。`AttachmentMessageHelper` 会把这些提示
统一追加到用户文本末尾。

该链路让 Agent 知道“本轮存在附件”，但用户无法在文案中明确表达“这句话参照哪一个附件”。
当一轮包含多个图片或文件时，纯自然语言的“第一张”“第二个文件”容易与附件顺序、文件名或
后续编辑脱节。

## 2. 目标

本次改造需要满足：

1. 用户在当前 Chat 草稿中输入 `@` 时，可选择本轮已经上传完成的附件。
2. 选中的附件在输入框中显示为不可拆分的引用标签，例如 `@图片1`、`@文件1`。
3. 发送请求携带稳定的附件引用名，服务端向 Agent 明确解释引用名与实际附件的对应关系。
4. 多个同类附件、同名附件和粘贴生成的附件仍能得到唯一、稳定的引用名。
5. 保持现有上传、粘贴、视频理解、PDF、Sandbox 文件以及附件恢复链路兼容。
6. 输入和候选菜单支持键盘操作、中文输入法、暗色模式与窄屏布局。

## 3. 非目标

本次不做以下事项：

- 不增加或调整输入框底部的模型、温度、推理强度等参数。
- 不允许引用历史消息中的附件；候选范围只包含当前尚未发送的草稿附件。
- 不把 Agent 生成的 artifact 自动加入引用候选。
- 不改变对象存储、Sandbox TTL、附件恢复或多模态模型路由策略。
- 不重新设计整个 Chat 页面或 Agent Configuration 弹窗。

## 4. 方案选择

采用“富文本引用标签 + 现有附件协议的向后兼容扩展”。

没有采用普通 textarea 中插入纯文本 `@图片1` 的方案，因为普通文本可被局部编辑成无效引用，
也无法可靠保存附件身份。没有采用全新的 `content_parts` 消息协议，因为当前需求只需要在已有
附件列表上增加稳定别名；重写所有消息生产者和消费者会扩大兼容范围。

现有 Workflow 的 `VariableChipField` 已验证了 `contentEditable` 中平铺文本节点与不可编辑标签的
模式。Chat 使用独立组件复用该模式的交互原则，但不直接耦合 Workflow 的变量语法。

## 5. 前端交互

### 5.1 引用命名

附件上传进入草稿时，根据类型和当前草稿中的同类顺序分配一次引用名：

- 图片：`图片1`、`图片2`
- 视频：`视频1`、`视频2`
- PDF 和其他文档：`文件1`、`文件2`

引用身份使用现有 `PendingAttachment.id`，显示名与身份分离。删除前一个附件后不重排其余引用，
避免已经插入文案的标签指向发生变化。再次上传只分配未使用的新序号。同名文件不影响引用唯一性。

### 5.2 候选菜单

在富文本编辑器的普通文本位置输入 `@` 时，打开当前草稿附件菜单：

- 只列出上传完成的附件；上传中的附件显示在附件区，但不可被引用。
- 每项显示类型缩略图或图标、引用名和原文件名。
- 上下方向键移动高亮，`Enter` 或 `Tab` 插入，`Escape` 关闭，鼠标点击可选择。
- 没有可引用附件时显示“先上传素材”的说明，不吞掉用户输入的 `@`。

选择后，用一个 `contentEditable=false` 标签替换触发用的 `@`。标签序列化为带 `@` 的可读文本，
并保留对应附件 ID。Backspace 或 Delete 一次删除整个标签；复制为可读的 `@图片1` 文本。

### 5.3 编辑器行为

编辑器保持现有行为：

- Enter 发送，Shift+Enter 换行；候选菜单打开时 Enter 优先选择候选。
- 粘贴图片继续触发上传；粘贴普通文本按纯文本处理并保留换行。
- `setDraft`、`reset`、禁用态和自动展开继续可用。
- 上传附件的展示移入或紧邻同一个输入容器；除引用标签与候选菜单外，不重做页面视觉层级。
- 标签和菜单使用现有主题变量，提供可见焦点、ARIA 角色和窄屏溢出处理。

## 6. 协议与服务端映射

在 `SendMessageRequest.SendMessageAttachment` 增加可选字段：

```text
reference_name: 图片1
```

前端发送所有当前附件；被文案引用的附件携带 `reference_name`，未引用附件保持字段为空。
旧客户端和其他 API 调用者无需修改。

服务端对 `reference_name` 执行长度、字符和重复校验，然后由
`AttachmentMessageHelper.buildMessageWithAttachments` 生成明确、无歧义的 Agent 材料说明：

```text
[Attached material reference: @图片1 = image file "menu.png" (image attachment 1)]
[Attached material reference: @文件1 = sandbox file "/tmp/data.xlsx"]
```

映射说明与原用户文案一起进入 Agent，但聊天历史只保存用户实际编辑的原文：

- 图片使用文件名和多模态附件顺序关联实际图片内容。
- 视频使用文件名关联后续生成的 `understand_video` 引用提示，不暴露对象存储 URL。
- PDF 关联现有文件 URL 提示。
- Sandbox 文件关联服务端计算的 `/tmp/<safe-file-name>` 路径。

附件没有 `reference_name` 时继续采用当前提示格式。引用名无效或重复时拒绝本次请求并返回明确的
客户端错误，避免模型收到表面存在但映射不确定的引用。

为避免用户重新打开会话后看到 URL、Sandbox 路径和机器映射，`SessionCommand` 同时携带：

- `message`：供 Agent 使用的增强文本。
- `displayMessage`：用户输入框序列化出的原始可读文本。

处理 Pod 用 `displayMessage` 作为显示内容、用 `message` 作为 Agent 内容写入
`ChatMessageService`，并用 `message` 调用 Agent。`ChatMessage` 增加可选字段 `agent_content`：

- `content`：聊天历史接口和会话标题使用的用户原文。
- `agent_content`：包含附件映射的 Agent 文本。

会话重建时优先恢复 `agent_content`，旧消息没有该字段时回退到 `content`。旧命令缺少
`displayMessage` 时同样回退到 `message`，保证滚动发布与历史数据兼容。新增字段为可选字符串，
不需要数据迁移或新索引。

## 7. 数据流

```text
上传附件
  -> 草稿附件获得稳定 id 和引用名
  -> 用户输入 @ 并选择附件
  -> 编辑器插入附件 id 绑定的引用标签
  -> 发送时序列化可读文案 + attachments.reference_name
  -> AttachmentMessageHelper 校验并构建引用映射
  -> 跨 Pod SessionCommand 携带 Agent 文本、显示文本和附件元数据
  -> Agent 同时收到文案、引用映射与实际多模态/文件内容
```

引用信息不写入新的 Mongo 集合。用户消息的 `content` 只保存可读的 `@图片1` 文案，机器映射
保存在同一消息的 `agent_content`；本次不要求重新打开历史消息后继续编辑原引用。

## 8. 错误处理与边界

- 附件仍在上传时禁止发送该引用；若用户已插入标签后附件被删除，标签同步从编辑器移除。
- 上传失败时不生成可选候选，也不保留悬空标签。
- 外部客户端提交空、超长、含换行/控制字符或重复的 `reference_name` 时返回 400。
- 用户直接输入形似 `@图片1` 的普通文本不自动获得附件身份；只有从候选菜单插入的标签才发送映射。
- 没有引用任何附件时，请求和 Agent 提示保持现有行为。
- 日志不得新增对象存储签名 URL、文件内容或凭据输出。

## 9. 测试策略

按 TDD 增加以下覆盖：

1. 前端纯函数和组件测试
   - 同类附件引用名唯一且删除后不重排。
   - 输入 `@` 打开候选并可用键盘选择。
   - 插入标签后序列化出正确文案和附件 ID。
   - 删除附件会清理相应标签。
   - 粘贴文本、Shift+Enter、粘贴图片和发送行为保持兼容。
2. `AttachmentMessageHelperTest`
   - 图片、视频、PDF 和 Sandbox 文件生成正确引用映射。
   - 无引用字段时输出保持兼容。
   - 非法和重复引用名失败关闭。
3. API 与命令链路回归
   - `reference_name` 跨 SSE 请求和跨 Pod 命令负载后仍与附件一致。
   - 多模态附件顺序不因映射生成而改变。
   - 历史接口读取 `content`，Agent 重建优先读取 `agent_content`；旧消息和旧命令仍可回退。
4. 验证命令
   - Frontend 目标测试、完整测试、lint 和 build。
   - Server 目标测试及 `:core-ai-server:check`。
5. 视觉检查
   - 亮色、暗色、窄屏下检查标签换行、候选定位、缩略图和键盘焦点。

## 10. 验收标准

1. 用户上传两张图片，输入 `@` 能看到 `图片1`、`图片2` 及各自文件名。
2. 文案可同时引用两个素材，发送后及重新打开会话时，聊天气泡只显示可读的 `@图片1`、`@图片2`。
3. Agent 实际输入中存在每个引用名到对应附件的明确映射，且图片顺序与映射一致。
4. 删除或上传失败的附件不会产生悬空引用。
5. 未使用 `@` 的原有附件发送行为不变。
6. 现有图片粘贴、视频理解、PDF、Sandbox 文件和附件恢复测试继续通过。
