## 0.1 认证体系概览

### 0.1.1 整体设计

core-ai-frontend 的认证系统采用**后端驱动**模式：前端不自行判断是否需要登录，而是先调用 `/api/capabilities` 获取服务端能力清单，再根据 `authRequired` 字段决定是否进入登录流程。

```
┌─────────────┐  1. fetchCapabilities()   ┌──────────┐
│   App.tsx   │ ──────────────────────────► │  后端    │
│             │ ◄────────────────────────── │ /api/    │
│             │  2. { authRequired: bool }  │ capabi.  │
└──────┬──────┘                            └──────────┘
       │
       │ authRequired=true?
       ▼
┌─────────────┐    3a. 自动登录     ┌──────────────┐
│ 无认证模式  │   （local 用户）    │  登录页面    │
│             │                     │  email/pwd   │
└─────────────┘                     └──────────────┘
```

💡 **设计意图**：让同一份前端代码既能跑在"开箱即用"的无认证环境（如本地开发、演示），也能跑在需要多用户管理的生产环境。切换完全由后端配置决定，前端无需重新构建。

### 0.1.2 核心文件一览

| 文件 | 职责 |
|------|------|
| `api/capabilities.ts` | 拉取服务端能力清单 |
| `api/auth.ts` | AuthContext、useAuth、用户存储 |
| `api/client.ts` | 通用 HTTP 请求、自动注入 Bearer、401 处理 |
| `api/permissions.ts` | `hasPermission()` 工具函数 |
| `components/RequirePermission.tsx` | 基于权限的组件守卫 |
| `pages/login/LoginPage.tsx` | 登录/注册 UI |
| `App.tsx` | 启动阶段的认证初始化 |

## 0.2 能力检查与启动流程

### 0.2.1 fetchCapabilities

```ts
// api/capabilities.ts
export interface Capabilities {
  chat: boolean
  traces: boolean
  prompts: boolean
  dashboard: boolean
  systemPrompts: boolean
  authRequired: boolean   // 关键字段：是否需要认证
}

export async function fetchCapabilities(): Promise<Capabilities> {
  const res = await fetch('/api/capabilities')
  if (!res.ok) throw new Error('Failed to fetch capabilities')
  return res.json()
}
```

💡 **设计意图**：`/api/capabilities` 是唯一一个**不需要鉴权**的接口，它的响应决定整个前端的行为模式。这样即便用户还没有登录，前端也能正确渲染 UI 框架（导航栏、侧边菜单）。

### 0.2.2 App.tsx 中的启动序列

```tsx
// App.tsx (简化)
const [user, setUser] = useState<AuthUser | null>(null)
const [caps, setCaps] = useState<Capabilities | null>(null)
const [loading, setLoading] = useState(true)

useEffect(() => {
  (async () => {
    // 第一步：获取能力清单
    const c = await fetchCapabilities()
    setCaps(c)

    if (!c.authRequired) {
      // 无认证模式：自动创建一个 "local" 虚拟用户
      const localUser: AuthUser = {
        apiKey: 'local',
        userId: 'local',
        name: 'Local User',
        permissions: ['*']   // 拥有所有权限
      }
      setUser(localUser)
    } else {
      // 认证模式：尝试从 localStorage 恢复
      const stored = getStoredUser()
      if (stored) {
        // 用 /api/auth/me 校验 token 是否仍然有效
        try {
          const me = await authApi.me()
          setUser({ ...stored, role: me.role, permissions: me.permissions })
        } catch {
          clearUser()   // token 过期，清除本地状态
        }
      }
    }
    setLoading(false)
  })()
}, [])
```

💡 **设计意图**：启动时不直接跳转登录页，而是先检查本地存储；如果有 token 就静默恢复会话，避免用户每次打开浏览器都要重新输入密码。

## 0.3 AuthContext 与 useAuth

### 0.3.1 AuthUser 接口

```ts
// api/auth.ts
export interface AuthUser {
  apiKey: string          // 用于 Bearer 鉴权的 token
  userId: string          // 用户唯一 ID
  name: string            // 显示名称
  role?: string           // 角色名（如 "admin"、"user"）
  permissions?: string[]  // 权限列表（如 ["chat.use", "agent.view"]）
}
```

### 0.3.2 AuthContext 定义

```ts
// api/auth.ts
import { createContext, useContext } from 'react'

export interface AuthContextType {
  user: AuthUser | null
  login: (user: AuthUser) => void
  logout: () => Promise<void>
  capabilities: Capabilities | null
}

export const AuthContext = createContext<AuthContextType>({
  user: null,
  login: () => {},
  logout: async () => {},
  capabilities: null
})

export function useAuth() {
  return useContext(AuthContext)
}
```

💡 **设计意图**：使用 React Context 而非全局状态库（Redux 等），保持轻量。认证状态是典型的"全局但低频更新"场景，Context 完全够用。

### 0.3.3 localStorage 存取

```ts
// api/auth.ts
const KEYS = {
  apiKey: 'apiKey',
  userId: 'userId',
  userName: 'userName',
  userRole: 'userRole',
  permissions: 'userPermissions'
}

export function getStoredUser(): AuthUser | null {
  const apiKey = localStorage.getItem(KEYS.apiKey)
  const userId = localStorage.getItem(KEYS.userId)
  const name = localStorage.getItem(KEYS.userName)
  const role = localStorage.getItem(KEYS.userRole) || undefined

  if (!apiKey || !userId) return null

  // 服务端模式下，'local' 这个特殊值不被接受
  if (apiKey === 'local') return null

  return {
    apiKey, userId, name: name || userId, role,
    permissions: getStoredPermissions()
  }
}

export function storeUser(
  apiKey: string, userId: string, name: string,
  role?: string, permissions?: string[]
) {
  localStorage.setItem(KEYS.apiKey, apiKey)
  localStorage.setItem(KEYS.userId, userId)
  localStorage.setItem(KEYS.userName, name)
  if (role) localStorage.setItem(KEYS.userRole, role)
  if (permissions) storePermissions(permissions)
}

export function clearUser() {
  Object.values(KEYS).forEach(k => localStorage.removeItem(k))
}

// 权限单独存取，因为登录接口一次性返回，但后续可能需要刷新
export function storePermissions(perms: string[]) {
  localStorage.setItem(KEYS.permissions, JSON.stringify(perms))
}

export function getStoredPermissions(): string[] | undefined {
  const raw = localStorage.getItem(KEYS.permissions)
  if (!raw) return undefined
  try { return JSON.parse(raw) } catch { return undefined }
}
```

💡 **设计意图**：`getStoredUser()` 中拒绝 `apiKey === 'local'` 是为了防止无认证模式下误存的虚拟用户信息污染正式的认证流程。

## 0.4 HTTP 客户端与鉴权

### 0.4.1 request 函数

```ts
// api/client.ts
async function request<T>(
  url: string,
  options?: RequestInit
): Promise<T> {
  const apiKey = localStorage.getItem('apiKey')
  const headers: Record<string, string> = {
    'Content-Type': 'application/json',
    ...(options?.headers as Record<string, string> || {})
  }

  // 自动注入 Bearer token（local 模式跳过）
  if (apiKey && apiKey !== 'local') {
    headers['Authorization'] = `Bearer ${apiKey}`
  }

  const res = await fetch(url, { ...options, headers })

  // 401 → 清除本地状态，跳转登录
  if (res.status === 401) {
    if (apiKey !== 'local') {
      clearUser()
      window.location.href = '/login'
    }
    throw new Error('Unauthorized')
  }

  if (!res.ok) {
    throw new Error(await errorMessage(res))
  }

  return res.json()
}
```

💡 **设计意图**：把"401 → 登出 → 跳转"这个逻辑集中在一处，所有 API 调用自动受益。如果分散在各个页面处理，很容易遗漏导致页面卡在异常状态。

### 0.4.2 errorMessage 解析

```ts
// api/client.ts
async function errorMessage(res: Response): Promise<string> {
  try {
    const body = await res.json()
    // 后端约定返回 { message: "xxx" }
    return body.message || res.statusText
  } catch {
    return res.statusText
  }
}
```

## 0.5 登录与注册流程

### 0.5.1 authApi

```ts
// api/client.ts
export const authApi = {
  login(email: string, password: string) {
    return request<{
      api_key: string
      user_id: string
      name: string
      role?: string
      permissions?: string[]
    }>('/api/auth/login', {
      method: 'POST',
      body: JSON.stringify({ email, password })
    })
  },

  register(email: string, password: string, name: string) {
    return request<{ message: string }>('/api/auth/register', {
      method: 'POST',
      body: JSON.stringify({ email, password, name })
    })
  },

  logout() {
    return request<{ message: string }>('/api/auth/logout', {
      method: 'POST'
    })
  },

  me() {
    return request<{
      user_id: string
      name: string
      role?: string
      permissions?: string[]
    }>('/api/auth/me')
  }
}
```

### 0.5.2 LoginPage 中的调用

```tsx
// pages/login/LoginPage.tsx (简化)
const { login } = useAuth()
const navigate = useNavigate()

const handleLogin = async (email: string, password: string) => {
  const res = await authApi.login(email, password)
  // 存入 localStorage
  storeUser(res.api_key, res.user_id, res.name, res.role, res.permissions)
  // 更新 React 状态
  login({
    apiKey: res.api_key,
    userId: res.user_id,
    name: res.name,
    role: res.role,
    permissions: res.permissions
  })
  navigate('/')
}
```

💡 **设计意图**：`login` 回调既更新 localStorage（持久化）又更新 React state（即时响应），二者缺一不可。只更新 state 会导致刷新后丢失登录；只更新 localStorage 会导致当前页面不刷新。

### 0.5.3 登录流程时序

```
用户输入 email/password
        │
        ▼
POST /api/auth/login ──────► 后端校验
        │                        │
        │  { api_key, user_id }  │ 创建 session/cookie
        ◄────────────────────────┘
        │
        ▼
storeUser() → localStorage
login()    → React state
navigate('/')
```

## 0.6 权限系统与 RBAC

### 0.6.1 权限字符串约定

权限采用 `resource:action` 格式，例如：

| 权限 | 含义 |
|------|------|
| `chat.use` | 使用聊天功能 |
| `agent.view` | 查看 Agent |
| `agent.create` | 创建 Agent |
| `workflow.edit` | 编辑工作流 |
| `system.manage` | 系统管理 |
| `user.manage` | 用户管理 |
| `*` | 所有权限（管理员/无认证模式） |

### 0.6.2 hasPermission 工具函数

```ts
// api/permissions.ts
export function hasPermission(
  userPermissions: string[] | undefined,
  requiredPermission: string
): boolean {
  if (!userPermissions) return false
  // '*' 通配符：拥有所有权限
  if (userPermissions.includes('*')) return true
  return userPermissions.includes(requiredPermission)
}
```

💡 **设计意图**：用简单的字符串数组匹配而非复杂的策略引擎，保持前端权限判断的轻量。复杂的 RBAC 角色→权限映射在后端完成，前端只负责"当前用户是否持有某权限"的最终判定。

## 0.7 RequirePermission 组件

### 0.7.1 组件实现

```tsx
// components/RequirePermission.tsx
import { useAuth } from '../api/auth'
import { hasPermission } from '../api/permissions'

interface Props {
  permission: string
  children: React.ReactNode
  fallback?: React.ReactNode  // 无权限时显示的替代内容
}

export function RequirePermission({ permission, children, fallback }: Props) {
  const { user } = useAuth()

  if (!hasPermission(user?.permissions, permission)) {
    return fallback ? <>{fallback}</> : null
  }

  return <>{children}</>
}
```

### 0.7.2 使用示例

```tsx
// 在侧边栏中：只有拥有 user.manage 权限的用户才看到"用户管理"入口
<RequirePermission permission="user.manage" fallback={null}>
  <SidebarLink to="/admin/users">用户管理</SidebarLink>
</RequirePermission>

// 在页面上：没有 chat.use 权限时显示提示
<RequirePermission
  permission="chat.use"
  fallback={<div className="p-8 text-center">暂无聊天权限</div>}
>
  <ChatMessagesPanel />
</RequirePermission>
```

💡 **设计意图**：声明式权限控制，比在组件内写 `if (hasPermission(...))` 更清晰。`fallback` prop 允许自定义无权限时的展示，而不是简单隐藏。

## 0.8 会话管理与登出

### 0.8.1 登出流程

```ts
// App.tsx 中的 logout 回调
const logout = async () => {
  try {
    // 先通知后端销毁 session
    await authApi.logout()
  } catch {
    // 即使后端调用失败，也要清除本地状态
  } finally {
    clearUser()
    setUser(null)
  }
}
```

💡 **设计意图**：登出采用"尽力而为"策略——即便后端不可达（比如网络断了），也要清除本地的 token，防止下次打开时误用过期凭证。

### 0.8.2 Session Cookie

后端在登录成功后会设置 HTTP-only cookie 作为 session 标识。`authApi.logout()` 会通知后端使该 session 失效。cookie 由浏览器自动管理，前端代码无需直接操作。

## 0.10 常见陷阱与调试

### 0.10.1 刷新后丢失登录

**原因**：`storeUser()` 没有被调用，只更新了 React state。

**调试**：
```js
// 在浏览器 Console 执行
localStorage.getItem('apiKey')  // 如果为 null，说明没有持久化
```

### 0.10.2 无限重定向到 /login

**原因**：`request()` 中 401 处理与 `authApi.me()` 冲突——`me()` 返回 401 时触发 `clearUser()` + 跳转，但跳转后又触发 `me()`。

**解决**：`request()` 中的 401 处理会跳过 `apiKey === 'local'` 的情况；正常认证模式下，`App.tsx` 在 `me()` 失败时会调用 `clearUser()` 但不主动跳转，而是等 `user === null && authRequired` 时由路由守卫跳转。

### 0.10.3 权限不生效

**原因**：登录接口返回的 `permissions` 没有传入 `storeUser()`。

**调试**：
```js
JSON.parse(localStorage.getItem('userPermissions'))
// 检查是否为期望的权限数组
```
