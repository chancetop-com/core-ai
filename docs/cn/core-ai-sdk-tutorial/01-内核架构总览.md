## 1.1 内核模块定位

### 1.1.1 core-ai 是什么

`core-ai` 模块是整个 core-ai 框架的**引擎本体**，提供：

- **Agent 运行时**：agent loop、turn 调度、生命周期管理
- **工具系统**：工具定义、注册、派发、并发编排
- **LLM 抽象**：统一的 LLM 调用接口，支持多 vendor
- **记忆与 RAG**：对话历史、向量检索、检索增强生成
- **编排系统**：单 agent 循环、多节点 DAG（Flow）、跨 agent（A2A）
- **可观测性**：OpenTelemetry 集成、全链路追踪
- **扩展机制**：lifecycle 钩子、Provider SPI、插件系统

### 1.1.2 内核 vs 宿主

```
┌─────────────────────────────────────────────────┐
│              宿主应用（Host Application）          │
│                                                   │
│   ┌─────────────┐  ┌─────────────┐  ┌──────────┐ │
│   │ core-ai-    │  │ core-ai-    │  │ core-ai- │ │
│   │ server      │  │ cli         │  │ benchmark│ │
│   │ (HTTP+SSE)  │  │ (REPL+ACP)  │  │ (BFCL)   │ │
│   └──────┬──────┘  └──────┬──────┘  └────┬─────┘ │
│          │                │               │       │
│          └────────┬───────┴───────────────┘       │
│                   │ load(new MultiAgentModule())  │
│                   ▼                                │
│   ┌─────────────────────────────────────────────┐ │
│   │           core-ai（内核引擎）                 │ │
│   │                                             │ │
│   │  Agent / Tool / LLM / Memory / Flow / MCP  │ │
│   │  Skill / Session / Telemetry / Persistence │ │
│   └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
```

💡 **设计意图**：内核是**库（library）**，宿主是**应用（application）**。宿主只需 `load(new MultiAgentModule())` 就能拿到整套能力，无需关心内部实现。

### 1.1.3 内核的边界

**内核负责**：
- Agent 生命周期管理（创建、运行、销毁）
- 工具定义与派发
- LLM 调用与响应解析
- 对话历史与记忆
- 遥测与追踪

**内核不负责**：
- HTTP 服务（由 `core-ai-server` 提供）
- 用户交互界面（由 `core-ai-frontend` 提供）
- 代码执行沙箱（由 `core-ai-sandbox-runtime` 提供）
- 持久化存储的具体实现（内核提供 SPI，宿主提供实现）

## 1.4 设计原则

### 1.4.1 Provider SPI 模式

**所有子系统都遵循同一套形态**：

```
Registry（注册表）
  └─ Provider（抽象接口/基类）
       └─ ConcreteProvider（具体实现）
```

**示例**：

| 子系统 | Registry | Provider | ConcreteProvider |
|---|---|---|---|
| LLM | `LLMProviders` | `LLMProvider` | `LiteLLMProvider` |
| Persistence | `PersistenceProviders` | `PersistenceProvider` | `FilePersistenceProvider`、`RedisPersistenceProvider` |
| VectorStore | `VectorStores` | `VectorStore` | `MilvusVectorStore`、`HnswLibVectorStore` |
| Tool | `ToolRegistry` | `ToolProvider` | `BuiltinToolProvider`、`McpToolProvider` |
| Skill | `SkillRegistry` | `SkillProvider` | `FileSkillProvider` |
| Tracer | `TracerRegistry` | `Tracer` | `AgentTracer`、`LLMTracer`、`FlowTracer` |

💡 **设计意图**：统一的 SPI 形态让扩展变得简单——只需实现 Provider 接口，注册到 Registry，就能替换默认实现。

### 1.4.2 Lifecycle 钩子链

**所有横切逻辑都通过 lifecycle 钩子织入**，而不是硬编码在 agent loop 里。

```
Agent/ToolExecutor/ModelGateway
  └─ 调用 lifecycle.beforeXxx() / afterXxx()
       └─ 具体 Lifecycle 实现（Compression / DoomLoop / Reflection）
```

**好处**：
- **解耦**：压缩、死循环检测、reflection 等逻辑互不干扰
- **可扩展**：你可以写自己的 lifecycle，注册到 `AgentBuilder`
- **可测试**：每个 lifecycle 可以独立测试

💡 **设计意图**：这是内核**最重要的扩展点**。80% 的定制需求都可以通过 lifecycle 实现。

### 1.4.3 Builder + Assembler 分离

- **Builder**：流式 API，收集用户配置（如 `AgentBuilder.systemPrompt(...).tool(...)`）
- **Assembler**：终局组装，统一施加默认值、终止条件、memory、reflection

```
AgentBuilder  ──→  AgentAssembler.assemble()  ──→  Agent
  (用户配置)          (施加默认值/横切逻辑)         (最终实例)
```

💡 **设计意图**：Builder 负责"用户想要什么"，Assembler 负责"系统应该怎么做"。分离后，用户可以只关注业务逻辑，系统自动处理横切关注点。

### 1.4.4 三层编排

1. **单 agent 循环**：`Agent` + `ModelGateway` + `ToolOrchestration`
   - 一个 agent 内部，turn-by-turn 与 LLM 交互
   - 工具并发执行（按 concurrencyGroup 分批）

2. **多节点 DAG**：`Flow` + `FlowNode` + `FlowEdge`
   - 多个 agent/节点通过边连接成 DAG
   - 支持条件分支、并行、循环

3. **跨 agent**：`A2A`（Agent-to-Agent）
   - 远端 agent 暴露成 `A2ARemoteAgentToolCall`
   - 本地 agent 像调工具一样调远端 agent

💡 **设计意图**：三层编排覆盖所有场景——单 agent、多 agent 协作、跨服务 agent。

### 1.4.5 不可变配置 + 可变状态

- **不可变配置**：`systemPrompt`、`model`、`temperature` 等在 build 后不可变
- **可变状态**：`messages`、`nodeStatus`、`input`/`output` 在运行时变化

💡 **设计意图**：配置不可变保证线程安全，状态可变支持运行时交互。

**核心类**：
- `ToolCall`：工具抽象，子类实现 `execute(args)`
- `ToolRegistry`：中央注册表，管理所有工具
- `ToolProvider`：工具来源 SPI，提供工具列表
- `ToolExecutor`：执行单个工具
- `ToolOrchestration`：并发编排，按 concurrencyGroup 分批
