## 1.1 架构设计原则

### 1.1.1 核心原则

core-ai-server 的架构设计遵循以下原则:

1. **模块化** - 功能按职责划分为独立模块，降低耦合度
2. **依赖注入** - 使用 core-ng 框架的 DI 容器管理组件生命周期
3. **面向接口** - 核心组件都定义接口，便于测试和扩展
4. **分层清晰** - 严格区分业务逻辑、数据访问、传输层
5. **可扩展** - 通过模块机制轻松添加新功能

💡 **设计意图**: 这些原则确保系统易于维护、测试和扩展，支持团队协作开发。

### 1.1.2 设计模式

架构中使用了以下设计模式:

| 模式 | 应用场景 | 示例 |
|------|---------|------|
| **模块化** | 功能组织 | Module 机制 |
| **依赖注入** | 组件管理 | @Inject 注解 |
| **策略模式** | 算法切换 | LLM Provider |
| **观察者模式** | 事件处理 | SSE、事件发布 |
| **工厂模式** | 对象创建 | Agent 构建 |
| **装饰器模式** | 功能增强 | 中间件链 |

## 1.2 分层架构

### 1.2.1 四层架构

```
┌─────────────────────────────────────────┐
│         传输层 (Transport Layer)         │  ← HTTP/SSE/WebSocket
├─────────────────────────────────────────┤
│         应用层 (Application Layer)       │  ← Web Service 实现
├─────────────────────────────────────────┤
│         领域层 (Domain Layer)            │  ← 业务逻辑、领域服务
├─────────────────────────────────────────┤
│         基础设施层 (Infrastructure)      │  ← 数据库、缓存、外部服务
└─────────────────────────────────────────┘
```

### 1.2.2 各层职责

#### 传输层 (Transport Layer)

**职责**: 处理 HTTP 请求和响应

**核心组件**:
- `WebModule` - 静态文件和 SPA 路由
- `SseEndpointRegistry` - SSE 端点注册
- HTTP 路由和控制器

**示例代码**:
```java
// WebModule.java
http().route(HTTPMethod.GET, "/api/agents/:id", agentController::get);
registry.register(HTTPMethod.PUT, "/api/sessions/events", 
    SseBaseEvent.class, bind(AgentSessionChannelListener.class));
```

#### 应用层 (Application Layer)

**职责**: 实现 Web Service 接口，协调领域服务

**核心组件**:
- `*WebServiceImpl` - Web Service 实现类
- 请求/响应转换
- 事务管理

**示例代码**:
```java
// ChatSessionWebServiceImpl.java
public class ChatSessionWebServiceImpl implements ChatSessionWebService {
    @Inject AgentSessionManager sessionManager;
    
    public SessionDTO createSession(CreateSessionRequest request) {
        var session = sessionManager.createSession(request);
        return SessionMapper.toDTO(session);
    }
}
```

#### 领域层 (Domain Layer)

**职责**: 核心业务逻辑和领域模型

**核心组件**:
- `AgentSessionManager` - 会话管理
- `WorkflowEngine` - 工作流引擎
- `GatewayRoutingEngine` - LLM 路由
- 领域实体和值对象

**示例代码**:
```java
// AgentSessionManager.java
public class AgentSessionManager {
    public InProcessAgentSession createSession(AgentDefinition agent, User user) {
        var session = new InProcessAgentSession(agent, user);
        sessionRegistry.register(session);
        return session;
    }
}
```

#### 基础设施层 (Infrastructure Layer)

**职责**: 与外部系统交互

**核心组件**:
- `MongoCollection<T>` - MongoDB 访问
- `RedisClient` - Redis 访问
- `LLMProvider` - LLM 服务调用
- `SandboxService` - 沙箱服务

**示例代码**:
```java
// MongoDB 访问
@Inject MongoCollection<AgentDefinition> agentCollection;

public AgentDefinition findById(String id) {
    return agentCollection.find(Filters.eq("_id", id)).first();
}
```

### 1.2.3 层间依赖规则

```
传输层 → 应用层 → 领域层 → 基础设施层
   ↓         ↓         ↓           ↓
  只能      只能      可以         不依赖
  依赖      依赖      依赖         上层
  下层      下层      下层
```

⚠️ **严格规则**: 上层可以依赖下层，下层不能依赖上层。

## 1.4 模块依赖关系

### 1.4.1 加载顺序

从 `ServerApp.java` 可以看到模块的加载顺序:

```java
// 1. 系统模块
load(new SystemModule("sys.properties"));
loadProperties("agent.properties");

// 2. MongoDB 注册
registerMongo();

// 3. 核心 SDK 模块
load(new MultiAgentModule());
load(new ServiceApiModule());
load(new McpServerModule());

// 4. 平台基础设施模块（17个）
loadPlatformInfrastructure();

// 5. 领域模块（13个）
loadDomainModules();

// 6. 传输模块
loadTransportModules();
```

### 1.4.2 依赖关系图

```
ServerApp
    │
    ├── SystemModule (系统配置)
    │
    ├── MultiAgentModule (核心 SDK)
    │   ├── McpServerModule (MCP 服务器)
    │   └── ServiceApiModule (API 定义)
    │
    ├── 平台基础设施层
    │   ├── SettingsModule
    │   ├── AuthModule ← UserModule
    │   ├── GatewayModule ← LLMProvider
    │   ├── TraceModule ← IngestService
    │   ├── SandboxModule
    │   └── ... (其他基础模块)
    │
    ├── 领域层
    │   ├── SessionModule ← AgentSessionManager
    │   │   ├── ToolRegistryModule
    │   │   ├── SkillModule
    │   │   └── SandboxModule
    │   │
    │   ├── WorkflowModule ← WorkflowEngine
    │   │   ├── AgentRunnerModule
    │   │   ├── ToolRegistryModule
    │   │   └── SandboxModule
    │   │
    │   ├── AgentRunnerModule ← AgentRunner
    │   │   ├── SessionModule
    │   │   └── TraceModule
    │   │
    │   └── ... (其他领域模块)
    │
    └── WebModule (传输层)
        └── 依赖所有应用层模块
```

### 1.4.3 关键依赖说明

**SessionModule 依赖**:
```
SessionModule
├── ToolRegistryModule (工具注册)
├── SkillModule (技能加载)
├── SandboxModule (沙箱环境)
├── AuthModule (权限检查)
├── TraceModule (追踪记录)
└── MessagingInfrastructureModule (事件发布)
```

**WorkflowModule 依赖**:
```
WorkflowModule
├── AgentRunnerModule (执行 Agent 节点)
├── ToolRegistryModule (执行工具节点)
├── SandboxModule (执行代码节点)
├── TraceModule (追踪记录)
└── DatasetModule (数据集访问)
```

💡 **设计意图**: 通过明确的依赖关系，确保模块间的职责清晰，避免循环依赖。

## 1.5 数据流架构

### 1.5.1 会话数据流

```
用户请求
    ↓
┌─────────────────┐
│  HTTP/SSE 请求   │  ← 传输层
└────────┬────────┘
         ↓
┌─────────────────┐
│ WebServiceImpl  │  ← 应用层
│  (参数验证)      │
└────────┬────────┘
         ↓
┌─────────────────┐
│ AgentSession    │  ← 领域层
│   Manager       │
│  (业务逻辑)      │
└────────┬────────┘
         ↓
    ┌────┴────┐
    ↓         ↓
┌────────┐ ┌────────┐
│ MongoDB│ │ Redis  │  ← 基础设施层
│(持久化) │ │(缓存)  │
└────────┘ └────────┘
```

### 1.5.2 工作流执行流

```
WorkflowDefinition
    ↓
┌─────────────────┐
│ WorkflowEngine  │
│  (解析 DAG)     │
└────────┬────────┘
         ↓
┌─────────────────┐
│ NodeExecutor    │
│  (执行节点)     │
└────────┬────────┘
         ↓
    ┌────┴────┬────────┐
    ↓         ↓        ↓
┌────────┐ ┌────────┐ ┌────────┐
│ Agent  │ │  Tool  │ │  Code  │
│ 节点   │ │  节点  │ │  节点  │
└────────┘ └────────┘ └────────┘
    ↓         ↓        ↓
    └────┬────┴────────┘
         ↓
┌─────────────────┐
│ 结果聚合 & 存储 │
└─────────────────┘
```

## 1.6 技术栈选择

### 1.6.1 核心技术栈

| 层次 | 技术 | 版本 | 选择理由 |
|------|------|------|---------|
| **语言** | Java | 21 | 虚拟线程、模式匹配、性能优秀 |
| **框架** | core-ng | 最新 | 轻量级、高性能、模块化 |
| **数据库** | MongoDB | 6.0+ | 灵活 Schema、高可用、易扩展 |
| **缓存** | Redis | 6.0+ | 高性能、Pub/Sub、分布式锁 |
| **构建** | Maven | 3.8+ | 依赖管理、多模块支持 |
| **测试** | JUnit 5 | 最新 | 参数化测试、断言库 |
| **日志** | SLF4J + Logback | 最新 | 标准接口、灵活配置 |

### 1.6.2 为什么选择 core-ng 而非 Spring Boot

| 特性 | core-ng | Spring Boot |
|------|---------|-------------|
| **启动速度** | ⚡ 快 (1-2s) | 🐢 慢 (5-10s) |
| **内存占用** | 💚 低 (50-100MB) | 🔴 高 (200-500MB) |
| **模块化** | ✅ 原生支持 | ⚠️ 需要额外配置 |
| **学习曲线** | 📈 平缓 | 📈 陡峭 |
| **生态** | 🔸 较小 | 🔹 丰富 |

💡 **设计意图**: core-ng 更适合构建高性能、轻量级的微服务，而 Spring Boot 更适合大型企业应用。

### 1.6.3 为什么选择 MongoDB 而非 MySQL

| 特性 | MongoDB | MySQL |
|------|---------|-------|
| **Schema** | 灵活 | 严格 |
| **扩展性** | 水平扩展 | 垂直扩展 |
| **查询** | 丰富 | SQL |
| **事务** | 支持 (4.0+) | 强一致 |
| **适用场景** | 文档、会话 | 金融、订单 |

💡 **设计意图**: Agent 会话数据结构灵活，且需要水平扩展，MongoDB 更适合。

## 1.7 架构优势

### 1.7.1 模块化优势

✅ **独立开发** - 各模块可以独立开发和测试  
✅ **易于理解** - 职责清晰，降低认知负担  
✅ **便于维护** - 修改一个模块不影响其他模块  
✅ **支持扩展** - 新增功能只需添加新模块

### 1.7.2 分层优势

✅ **职责分离** - 每层只关注自己的职责  
✅ **依赖清晰** - 上层依赖下层，反向禁止  
✅ **易于测试** - 可以 Mock 下层依赖  
✅ **技术替换** - 可以替换某一层的实现

### 1.7.3 依赖注入优势

✅ **解耦** - 组件之间通过接口交互  
✅ **可测试** - 可以轻松注入 Mock 对象  
✅ **灵活** - 可以动态切换实现  
✅ **集中管理** - 容器统一管理生命周期

### 1.7.4 事件驱动优势

✅ **异步处理** - 不阻塞主流程  
✅ **松耦合** - 事件发布者不关心订阅者  
✅ **可扩展** - 可以轻松添加新的订阅者  
✅ **实时性** - SSE 提供实时推送
