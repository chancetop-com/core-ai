## 8.1 分布式部署概述

### 8.1.1 为什么需要分布式部署

随着 AI 应用规模的增长，单节点部署面临以下挑战：

| 挑战 | 说明 | 分布式解决方案 |
|------|------|---------------|
| **性能瓶颈** | 单节点 CPU/内存有限 | 水平扩展，多节点并行处理 |
| **可用性** | 单点故障导致服务中断 | 多副本部署，故障自动转移 |
| **可扩展性** | 无法应对流量峰值 | 弹性伸缩，按需扩容 |
| **地理分布** | 用户分布广泛，延迟高 | 多区域部署，就近访问 |
| **维护窗口** | 更新需要停机 | 滚动更新，零停机部署 |

💡 **核心价值**: 分布式部署让 core-ai-server 能够支撑大规模生产环境。

### 8.1.3 core-ai-server 的分布式支持

core-ai-server 通过以下机制支持分布式部署：

```java
// 1. 无状态设计 - 会话状态存储在 Redis
public class SessionService {
    @Inject
    private RedisClient redisClient;
    
    public void saveSession(String sessionId, Session session) {
        redisClient.set("session:" + sessionId, JsonUtil.toJson(session));
    }
}

// 2. 分布式锁 - 防止并发冲突
public class TaskScheduler {
    @Inject
    private DistributedLock lock;
    
    public void scheduleTask(String taskId) {
        lock.tryLock("task:" + taskId, () -> {
            // 执行任务调度
        });
    }
}

// 3. 事件发布 - 节点间通信
public class EventPublisher {
    @Inject
    private RedisClient redisClient;
    
    public void publish(String channel, Event event) {
        redisClient.publish(channel, JsonUtil.toJson(event));
    }
}
```

💡 **设计意图**: 
- 无状态设计：应用节点不保存状态，状态存储在 Redis
- 分布式协调：使用 Redis 实现分布式锁和事件发布
- 数据共享：MongoDB 作为共享数据存储

### 8.2.2 组件职责

| 组件 | 职责 | 部署方式 |
|------|------|---------|
| **负载均衡器** | 请求分发、SSL 终止、健康检查 | 独立部署（Nginx/云 LB） |
| **应用节点** | 处理业务逻辑、API 请求 | 多实例水平扩展 |
| **MongoDB** | 持久化数据存储 | 副本集或分片集群 |
| **Redis** | 缓存、会话、分布式锁 | 集群模式 |
| **对象存储** | 文件、归档数据存储 | 云服务或独立部署 |

### 8.2.3 流量路由策略

```yaml
# 负载均衡策略配置
loadbalancer:
  # 会话亲和性 - 确保同一用户的请求路由到同一节点
  session-affinity:
    enabled: true
    type: cookie  # cookie / ip_hash
    cookie-name: CORE_AI_SESSION
    timeout: 3600  # 1 小时
  
  # 健康检查
  health-check:
    enabled: true
    path: /health
    interval: 30s
    timeout: 5s
    unhealthy-threshold: 3
  
  # 负载均衡算法
  algorithm: least_connections  # round_robin / least_connections / ip_hash
```

💡 **设计要点**:
- **会话亲和性**: WebSocket 连接需要保持在同一节点
- **健康检查**: 自动摘除不健康节点
- **负载均衡**: 根据节点负载动态分配请求

## 8.3 容器化部署

### 8.3.1 Dockerfile

```dockerfile
# 构建阶段
FROM maven:3.9-eclipse-temurin-21 AS builder

WORKDIR /build

# 复制 pom 文件，下载依赖
COPY pom.xml .
COPY core-ai/pom.xml core-ai/
COPY core-ai-server/pom.xml core-ai-server/

RUN mvn dependency:go-offline -B

# 复制源码并构建
COPY . .
RUN mvn clean package -DskipTests -B

# 运行阶段
FROM eclipse-temurin:21-jre

WORKDIR /app

# 创建非 root 用户
RUN groupadd -r coreai && useradd -r -g coreai coreai

# 复制构建产物
COPY --from=builder /build/core-ai-server/target/core-ai-server-*.jar app.jar

# 复制配置文件
COPY core-ai-server/src/main/resources/application.yml /app/config/

# 设置权限
RUN chown -R coreai:coreai /app

# 切换到非 root 用户
USER coreai

# 暴露端口
EXPOSE 8080

# 健康检查
HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1

# 启动命令
ENTRYPOINT ["java"]
CMD ["-Xms512m", "-Xmx2g", \
     "-XX:+UseG1GC", \
     "-XX:MaxGCPauseMillis=200", \
     "-Djava.security.egd=file:/dev/./urandom", \
     "-jar", "app.jar", \
     "--spring.config.location=/app/config/"]
```

💡 **最佳实践**:
- **多阶段构建**: 减小最终镜像大小
- **非 root 用户**: 提高安全性
- **健康检查**: Docker 自动检测容器健康状态
- **JVM 参数优化**: 合理的内存和 GC 配置

### 8.3.3 Nginx 配置

```nginx
# nginx/nginx.conf
events {
    worker_connections 1024;
}

http {
    upstream core_ai_backend {
        # 负载均衡算法
        least_conn;
        
        # 应用节点
        server app1:8080 max_fails=3 fail_timeout=30s;
        server app2:8080 max_fails=3 fail_timeout=30s;
        
        # 会话亲和性（基于 cookie）
        sticky cookie srv_id expires=1h path=/;
    }
    
    # HTTP 重定向到 HTTPS
    server {
        listen 80;
        server_name api.core-ai.com;
        return 301 https://$server_name$request_uri;
    }
    
    # HTTPS 服务
    server {
        listen 443 ssl http2;
        server_name api.core-ai.com;
        
        # SSL 配置
        ssl_certificate /etc/nginx/ssl/cert.pem;
        ssl_certificate_key /etc/nginx/ssl/key.pem;
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_ciphers HIGH:!aNULL:!MD5;
        
        # 请求体大小限制
        client_max_body_size 100M;
        
        # 代理配置
        location / {
            proxy_pass http://core_ai_backend;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            
            # WebSocket 支持
            proxy_http_version 1.1;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection "upgrade";
            
            # 超时配置
            proxy_connect_timeout 60s;
            proxy_send_timeout 60s;
            proxy_read_timeout 60s;
        }
        
        # 健康检查端点
        location /health {
            proxy_pass http://core_ai_backend/health;
            access_log off;
        }
    }
}
```

💡 **配置要点**:
- **least_conn**: 最少连接数算法，平衡负载
- **sticky cookie**: 会话亲和性，保持 WebSocket 连接
- **WebSocket 支持**: 升级 HTTP 连接
- **SSL 终止**: Nginx 处理 SSL，后端使用 HTTP

```java
@Configuration
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    private Integer maxConcurrentSessions = 100;

    private List<String> allowedOrigins = List.of("*");
    
    // getters and setters

@Service

}
```

## 8.7 负载均衡

### 8.7.1 负载均衡策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **轮询** | 依次分配请求 | 节点性能相近 |
| **最少连接** | 分配给连接数最少的节点 | 长连接场景 |
| **IP 哈希** | 同一 IP 路由到同一节点 | 会话亲和性 |
| **加权轮询** | 按权重分配 | 节点性能差异大 |

### 8.7.2 会话亲和性

```yaml
# Nginx 会话亲和性配置
upstream backend {
    # 基于 cookie 的会话亲和性
    sticky cookie srv_id expires=1h path=/;
    
    server app1:8080;
    server app2:8080;
}
```

💡 **注意**: WebSocket 连接需要会话亲和性，确保连接保持在同一节点。

### 8.9.2 故障转移

```java
// 自动故障检测和转移
@Service
public class SessionService {
    @Retryable(
        value = {SessionNotFoundException.class},
        maxAttempts = 3,
        backoff = @Backoff(delay = 1000)
    )
    public Session getSession(String sessionId) {
        // 尝试从多个节点获取
        return sessionRepository.findById(sessionId);
    }
}
```

### 8.9.3 熔断机制

```java
// Resilience4j 熔断器
@CircuitBreaker(name = "mongodb", fallbackMethod = "fallback")
@Retry(name = "mongodb")
public List<Session> getSessions() {
    return sessionRepository.findAll();
}

public List<Session> fallback(Exception e) {
    // 降级处理
    return Collections.emptyList();
}
```

💡 **高可用原则**:
- 多副本部署，避免单点故障
- 自动故障检测和转移
- 熔断和降级，防止级联故障
- 数据冗余，确保数据安全

## 8.13 故障排查

### 8.13.1 Pod 启动失败

```bash
# 查看 Pod 状态
kubectl get pods -l app=core-ai-server

# 查看 Pod 日志
kubectl logs -f deployment/core-ai-server

# 查看 Pod 事件
kubectl describe pod <pod-name>

# 常见问题
# - ImagePullBackOff: 镜像拉取失败，检查镜像名称和仓库权限
# - CrashLoopBackOff: 应用启动失败，查看日志排查
# - Pending: 资源不足，检查节点资源或扩容
```

### 8.13.2 性能问题

```bash
# 查看资源使用
kubectl top pods -l app=core-ai-server

# 查看 HPA 状态
kubectl get hpa core-ai-hpa

# 查看应用指标
kubectl port-forward svc/core-ai-service 8080:80
curl http://localhost:8080/actuator/metrics

# 常见问题
# - CPU 使用率高: 优化代码或增加副本
# - 内存泄漏: 检查 JVM 堆内存，调整 -Xmx 参数
# - 响应慢: 检查数据库连接、Redis 缓存命中率
```

### 8.13.3 网络问题

```bash
# 测试服务连通性
kubectl exec -it <pod-name> -- curl http://core-ai-service:8080/health

# 检查 Service
kubectl get svc core-ai-service
kubectl describe svc core-ai-service

# 检查 Ingress
kubectl get ingress core-ai-ingress
kubectl describe ingress core-ai-ingress

# 常见问题
# - Service 无法访问: 检查 selector 和端口配置
# - Ingress 404: 检查路径和后端服务配置
# - DNS 解析失败: 检查 CoreDNS 配置
```
